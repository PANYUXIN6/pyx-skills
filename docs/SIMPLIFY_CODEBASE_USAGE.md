# simplify-codebase 使用说明

本文面向准备使用 `simplify-codebase` 的仓库维护者，不属于 Skill 的运行时指令。Skill 不会读取或依赖本文，仓库也无需完成本文列出的准备工作才能使用它。

## 什么时候使用

`simplify-codebase` 适合调查或删除已经出现消费者证据问题的生产代码，例如废弃 API、无生产消费者的旧实现、重复状态、过期兼容路径、无主抽象，以及它们独占的测试、文档、配置和依赖。

它不应成为每次任务或 Code Review 的固定阶段。普通未使用导入、格式问题、孤立 lint 告警和没有消费者证据的风格重构，留在日常开发或 Code Review 中处理即可。

## 调用方式

Skill 有两个相互独立的维度：

| 维度 | 选项 | 适用情况 |
| --- | --- | --- |
| 操作 | `audit` | 只调查和报告，不修改仓库；没有明确修改授权时默认使用。 |
| 操作 | `apply` | 用户明确要求在限定范围内执行删除或简化。 |
| 深度 | `light` | 当前任务、当前改动或一个局部候选，证据主要来自直接消费者和配套文件。 |
| 深度 | `deep` | 子系统或整个仓库，涉及跨包、动态加载、公共契约、持久化、线协议或生命周期。 |

不必在请求中使用内部模式名，只要把范围、是否允许修改和期望深度说清楚。例如：

```text
用 simplify-codebase 调查本次改动是否留下冗余代码，只报告，不修改。

用 simplify-codebase 清理本次任务产生的低风险孤儿代码；只修改消费者闭包已经证明为空的内容。

用 simplify-codebase 对支付子系统做完整 simplification 调查，读取仓库的防御模式和工具配置，但暂不修改。

用 simplify-codebase 深度清理这个仓库。允许删除证据充分、可恢复的低中风险候选；高影响或外部消费者不明确的候选只报告。
```

如果从 Code Review 中发现一个可能需要跨文件或跨包追踪的候选，可以单独发起清理请求。Code Review 本身不需要自动调用该 Skill。

## 仓库可以准备什么

没有任何强制准备项。缺少仓库策略时，Skill 仍可工作，但会保守推断，并把证据不足的候选标为延后处理。

对于大型 monorepo、动态加载较多，或包含持久化、异步生命周期和兼容逻辑的仓库，以下仓库自有信息可以显著提高判断置信度：

1. **仓库指令**：在 `AGENTS.md` 或等价文件中说明可用的验证命令、生成文件和迁移策略、受保护范围，以及允许的修改方式。
2. **防御模式记录**：记录取消、清理、幂等、竞态保护、首个终止事件、兼容逻辑等看似多余但实际承载约束的机制，并注明验证方式。
3. **分析工具配置**：为仓库实际使用的死代码、lint、重复检测和覆盖率工具配置真实入口、排除项与生成目录。工具由仓库选择，不要求照搬特定技术栈。
4. **聚合验证命令**：提供 `check`、`verify`、`run-gates` 或同类入口，把类型检查、lint、测试、构建和仓库专有一致性检查组合起来。
5. **当前契约资料**：维护仍然有效的公共 API、持久化格式、迁移、插件扩展点、架构决策和外部消费者说明。

文件名和工具名都只是示例。Skill 会发现并验证仓库已有事实，不会因为被调用就安装工具、创建政策文件、强制 100% 覆盖率或把其他仓库的门禁复制进来。

## 如何理解测试和覆盖率

- 测试存在，不代表被测试的功能必须保留。先判断该功能是否仍有生产消费者或当前契约；如果功能应删除，其独占测试通常也属于删除闭包。
- 未覆盖代码是调查信号，不是死代码证明。应先检查入口、动态注册、外部契约和运行时消费者，再决定删除、保留或延后。
- 仓库不需要达到 100% 覆盖率才能使用该 Skill。覆盖率的作用是补充风险证据，具体阈值、纳入范围和排除项由业务仓库决定。
- 不应为了让可疑代码显得合理而机械补测试，也不应仅凭未覆盖就删除代码。

## 输出应该包含什么

只读调查应说明范围、每个候选的消费者证据、删除/保留/延后结论、已执行检查和剩余不确定性。

获授权的清理还应说明候选与实际改动的对应关系、影响级别、使用的仓库规则、验证结果和恢复路径。没有强候选时，应明确报告没有发现值得清理的内容，而不是为了产生改动而删除代码。
